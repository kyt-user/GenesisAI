## 当前实现

### 1. 单次容量与累计用量分离

删除任务档位中的 `token_budget` 和累计用量 75% 收尾判断。累计输入、输出、总 token 继续记录，包括辅助摘要请求；模型轮次、工具次数、时间与连续失败限制继续生效。

`/budget` 分别展示累计用量、当前请求估算占用和容量。压缩不设置停止原因，也不改变开发完成状态；是否完成仍经过现有开发修改、验证和证据检查。

### 2. 请求准备时统一检查

自动压缩在模型请求前运行，统计系统提示、历史消息、工具调用参数、工具定义及恢复提示。默认使用序列化字符数 / 3 估算，并以实际 API 输入用量修正低估比例（1–4 倍）；切换模型时重置校准。

```python
input_limit = min(max_input_tokens, context_window - output_reserve_tokens)
input_limit -= safety_margin_tokens
effective_limit = input_limit / underestimate_factor
trigger = effective_limit * 0.90
target = trigger * 0.70

request = assemble(system, working_messages, tools, recovery_notice)
if estimate(request) >= trigger:
    message_target = target - estimate_fixed_overhead(request)
    working_messages = compact(working_messages, message_target)
    request = assemble_again(working_messages)
validate_size_and_tool_pairs(request)
send(request)
```

实际请求的 `max_tokens` 不超过输出预留，用户设置的更小输出值仍生效。必要系统提示、用户约束或证据无法安全放入时明确报错，不再退化成只保留用户问题。

### 3. 完整历史与工作上下文分开

`messages` 和 JSONL 原始日志保留完整历史；新增会话级 `context_checkpoint` 保存覆盖位置、历史前缀指纹及压缩消息。检查点不在新一轮用户请求时清空。

```python
if checkpoint and hash(history[:checkpoint.source_count]) == checkpoint.source_hash:
    working = checkpoint.messages + history[checkpoint.source_count:]
else:
    invalidate_checkpoint_if_present()
    working = copy(history)

projected = compact(working)
validate(projected)
save_checkpoint(source_count=len(history), source_hash=hash(history), messages=projected)
# 不覆盖或删除 history。
```

前缀发生变化会废弃缓存并从完整历史重建。检查点随会话保存和重载；没有历史格式迁移或兼容层，也没有清理已有用户数据。

### 4. 单个任务内部也能压缩

- 用户消息与约束保留；近期交互按预算保留。
- 一批并行工具调用与全部对应结果作为不可拆分单位，孤立、重复或尚未返回的结果不能发给模型。
- 较早工具结果提取执行事实：工具名、调用 ID、路径、变更哈希、成功与否、错误、测试退出码、统计和命令日志路径。
- 模型摘要只整理历史说明与下一步；确定性执行证据独立附带，不根据工具调用参数推断成功。
- `agentic` 模式调用同一模型产生摘要；摘要不可用、失败或截断时回退 `basic`。`basic` 不调用摘要模型，保留确定性证据与近期说明。
- 摘要不是完整历史副本。仅保留部分较近、较重要的证据，明确提示需要时回读原始日志或当前文件。
- 嵌套正文、stdout/stderr、长补丁等仅在摘要输入副本中缩减；原始消息不变。未达容量阈值时不再无条件把工具结果截成固定字符数。

### 5. 手动压缩与超限恢复

`/compact` 使用同一实现，以当前消息约一半作为目标（同时不超过自动目标），成功后保存检查点。短上下文本身无法进一步缩减时返回未折叠；尚有待确认工具时先完成确认，避免切断调用链。

API 明确报告上下文超限时，强制使用 `basic` 缩减后重试一次；仍超限、没有减少或必要内容放不下则明确报告 `context_error`，不无限重试。这个分支不调用可能同样超限的摘要模型。

```python
try:
    response = call_model(prepared_request)
except ContextWindowExceeded:
    smaller = compact(mode="overflow_recovery", strategy="basic")
    assert smaller.size < prepared_request.size
    response = retry_once(smaller)  # 再失败即停止并报告容量问题
```

## 配置入口

非交互 YAML 的 `context` 与终端持久化配置 JSON 的 `context` 使用相同字段：

```yaml
context:
  max_input_tokens: 400000
  context_window: 400000
  output_reserve_tokens: 4096
  safety_margin_tokens: 1024
  preserve_recent_tokens: 20000
  summary_max_tokens: 2048
  strategy: agentic
```

这些是应用的保守默认值，**不是 DeepSeek/Qwen 的模型规格**。本次没有引入在线模型目录，使用其他容量时应显式配置。切换为另一模型时清除旧模型的容量覆盖，采用应用默认值，避免继承错误的容量；用户可再设置该模型的 `context`。

## 图片输入扩展（2026-11-05）

文字与图片使用同一工作上下文，但预算分开计算。图片按尺寸作保守 patch 估算，再使用真实输入用量校准；不将 Base64 长度当作视觉 token。请求同时受图片数量、单张字节、解码像素、缩放最长边及图片总字节约束，`/budget` 展示图片数量、估算 token 和总字节。

最近用户消息的图片与本轮最新一批工具图片保持可见；剩余预算按新到旧保留历史图片，其他图片用包含 `image_ref` 的明确占位文字替换。主动或自动压缩会卸载较早图片像素，但完整会话与磁盘快照保留。模型需要查看这些图片时使用 `read_image(image_ref=...)`。当前必要图片本身超限时明确失败，不悄悄截掉图片。摘要只能保留已有观察和引用，不能从文件名推断视觉事实。

图片预算位于模型 `context` 配置：`max_images`、`max_image_bytes`、`max_image_pixels`、`image_max_side`、`max_request_image_bytes`、`max_pending_image_bytes`。默认分别为 null（不按张数限制）、10485760、32000000、1536、12582912、134217728。原图完整保存，1536 是默认视图长边；`read_image` 可从原图裁剪并指定 `max_side`。数量、请求字节和视觉 Token 预算控制本次发送像素，省略部分保留引用；待发送原图和预览的资源配额单独检查。会话恢复或切换模型后按当前预算重新投影；需要更小视图时按引用裁剪或缩放，原图不被替换。
