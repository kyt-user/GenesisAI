## 1. 项目概述

### 1.1 项目背景与目标

GenesisAI 是一个基于 ReAct 模式的单 Agent Python CLI 项目，当前记忆系统采用 **JSON 索引 + Markdown 正文** 双层文件存储架构。随着记忆条目增长和交互场景复杂化，现有架构暴露出存储性能、检索质量、生命周期管理等多维度瓶颈。

本次重构的核心目标：

| 目标 | 说明 |
|------|------|
| **性能** | 从全量 JSON 加载升级为 SQLite 按需查询，消除 I/O 瓶颈 |
| **检索质量** | 从 `\W+` 分词 AND 匹配升级为 FTS5 全文检索 + Embedding 语义检索 |
| **去重** | 引入精确去重 + 语义去重，杜绝重复记忆写入 |
| **上下文管理** | 实现三级压缩策略，长对话不再丢失关键信息 |
| **生命周期** | 引入记忆归档/遗忘/物理删除机制，自动管理记忆衰减 |
| **Prompt 注入** | 从粗放的全量按类型注入升级为按相关度选择的智能注入 |

### 1.2 当前系统问题分析

#### 问题 1：存储架构 — 全量加载性能瓶颈

当前 `MemoryManager.__init__()` 在初始化时调用 `_load()` 将整个 `index.json` 读入内存，每次 `add()`/`forget()`/`search()` 操作后调用 `_save()` 将全量数据写回磁盘。

```python
# manager.py 当前实现 — 全量加载
def _load(self):
    data = json.loads(self.index_path.read_text(encoding="utf-8"))
    self._validate(data)
    return data

def _save(self, *, removed_changes=()):
    self._validate(self.data)
    with self._write_lock():
        atomic_json(self.index_path, self.data)  # 全量写入
```

**影响**：1000 条记忆时，每次操作需序列化/反序列化完整索引，且文件锁竞争导致并发写入阻塞。

#### 问题 2：检索质量 — 中文完全无效

```python
# manager.py 当前搜索实现
def search(self, query="", *, type=None, limit=20):
    words = [word for word in re.split(r"\W+", query.casefold()) if word]
    # \W+ 按非字母数字分词，中文字符被当作分隔符
    # 所有词必须同时出现（AND 匹配），无模糊/部分匹配
    if words and not all(word in haystack for word in words):
        continue
```

**影响**：
- 中文查询 `"项目架构"` 被分词为空列表，返回全部记忆（无过滤）
- 英文查询 `"project architecture"` 要求两个词同时出现，过于严格
- 搜索范围仅限 `title + summary + keywords`，遗漏 `content` 中的关键信息
- 无相关性评分排序，仅简单计数匹配词数

#### 问题 3：无去重机制

`add()` 方法不检查是否已存在相同或相似的记忆条目，导致 Agent 多次观察到同一事实时反复写入。

#### 问题 4：无上下文压缩策略

`ContextBudgeter.compact()` 仅做简单的消息截断和首尾保留，没有基于 token 计数的分级压缩，长对话中早期关键信息（工具调用结果、用户偏好）容易丢失。

#### 问题 5：无记忆生命周期管理

记忆只有 `active` 和 `forgotten` 两种状态，无自动归档、衰减、物理删除机制。低价值记忆永久占用检索空间。

#### 问题 6：Prompt 注入粗放

`context_budgeter.py` 中记忆注入逻辑按类型全量选取最近更新的记忆，不考虑与当前查询的相关性：

```python
# context_budgeter.py 当前注入逻辑
summaries = manager.summaries_for(memory_types)  # 仅按类型 + 更新时间排序
if summaries:
    lines = [f"- [{s['type']}] {s['title']}: {s['summary']}" for s in summaries]
    addition = "\n\n## 项目记忆摘要\n" + "\n".join(lines)
```

## 2. 五层记忆架构

重构后的记忆系统采用五层记忆模型，模拟人类认知记忆分层机制，每层具有不同的内容范围、生命周期和存储方案。

### 2.1 层级定义

| 层次 | 内容 | 生命周期 | 存储方案 | 对应层级 |
|---|---|---|---|---|
| **L1 — 工作记忆** | 当前目标、计划、待办、工具结果 | 单次任务 | State Store (sessions/*.json) | 已有，小幅增强 |
| **L2 — 原始事件** | 用户消息、工具调用、文件修改、执行结果 | 长期保存，定期归档 | SQLite events 表 | 新建 |
| **L3 — 语义记忆** | 用户偏好、项目事实、技术栈 | 跨任务长期有效 | SQLite semantic_memories 表 + FTS5 + Embedding | 重构现有 |
| **L4 — 情景记忆** | 任务摘要、成败原因、关键决策 | 长期保存，定期压缩 | SQLite episodes 表 + FTS5 + 向量索引 | 新建 |
| **L5 — 程序记忆** | 操作规则、技能模板、踩坑记录 | 版本化长期保存 | Markdown + Git (skills/learned/) | 增强现有 |

### 2.2 层间流转规则

| 触发条件 | 流转方向 | 动作 |
|---|---|---|
| 任务执行中 | L3/L4/L5 → L1 | 检索相关记忆注入工作记忆 |
| 任务完成 | L1 → L2 | 记录原始事件 |
| 任务完成 | L1 → L4 | 提取情景记忆（摘要+教训） |
| L2 事件超 30 天 | L2 → L4 | 归档事件，生成情景摘要 |
| L4 同类情景 ≥ 3 条 | L4 → L5 | 提炼为程序记忆（技能） |
| 对话中识别到事实 | → L3 | 写入语义记忆 |
| 用户显式教导 | → L3 或 L5 | 写入语义/程序记忆 |
| 记忆强度衰减 | L3: active → archived → forgotten → 删除 | 生命周期管理 |
| 情景记忆超 60 天 | L4: active → compressed | 压缩旧情景 |

### 2.3 新增数据库表

- **`events`** — L2 原始事件表（id, session_id, run_id, event_type, payload JSON, tokens, created_at, archived）
- **`episodes`** — L4 情景记忆表（id, session_id, title, category, outcome, summary, key_decisions JSON, lessons JSON, tags, related_memories JSON, importance, access_count, status, created_at, updated_at, last_used_at）
- **`episodes_fts`** — L4 全文索引
- **`episode_embeddings`** — L4 向量缓存

### 2.4 新增文件

- `memory/events.py` — L2 原始事件存储
- `memory/episodic.py` — L4 情景记忆管理

## 3. 技术方案

### 3.1 数据库选型：SQLite + FTS5

**选型理由**：

| 考量 | SQLite | 替代方案（如 ChromaDB/FAISS） |
|------|--------|-------------------------------|
| 额外依赖 | **零** — Python 标准库自带 `sqlite3` | 需安装第三方包，增加包体积 |
| FTS5 支持 | **内置** — 支持 BM25 排序、中文 unicode61 | 需额外配置 tokenizer |
| 并发控制 | **WAL 模式** — 读写并发不阻塞 | 部分需额外部署服务 |
| 部署复杂度 | **单文件** — `memories.db` 随项目存储 | 需独立服务或额外运行时 |
| 向量检索 | 不原生支持，需应用层计算 | 原生支持 ANN |

**结论**：鉴于 GenesisAI 是单进程 CLI 工具、零额外依赖是硬约束，SQLite + FTS5 是唯一合理选择。向量检索在应用层通过 BLOB 存储 + numpy 余弦计算实现（P10 阶段可选引入 numpy 或 sentence-transformers）。

**向量序列化方式**：

```python
import struct

def embedding_to_blob(embedding: list[float]) -> bytes:
    """将浮点列表序列化为紧凑 BLOB。"""
    return struct.pack(f'{len(embedding)}f', *embedding)

def blob_to_embedding(blob: bytes) -> list[float]:
    """从 BLOB 反序列化为浮点列表。"""
    n = len(blob) // 4  # float32 = 4 bytes
    return list(struct.unpack(f'{n}f', blob))
```

```python
def create_connection(db_path: str) -> sqlite3.Connection:
```

### 3.3 混合检索方案

检索管线采用 **三路融合** 架构：

```
用户查询
    ├──→ [路径 A] FTS5 BM25 关键词检索 ──→ 候选集 A
    ├──→ [路径 B] Embedding 语义检索 ──→ 候选集 B（P10 可选）
    └──→ [融合层] Reciprocal Rank Fusion (RRF) ──→ 最终排序结果
```

#### 3.3.2 Embedding 语义检索（P10 可选实现）

```python
class EmbeddingRetriever:
    """基于 Embedding 的语义检索器（P10 阶段）。"""

    def __init__(self, conn: sqlite3.Connection):
        self.conn = conn
        self._model = None  # 延迟加载

    def search(self, query: str, *, limit: int = 20) -> list[dict]:
        query_embedding = self._encode(query)
        # 从 memory_embeddings 加载所有向量
        # 计算余弦相似度
        # 返回 top-K
        rows = self.conn.execute(
            "SELECT memory_id, embedding, dim FROM memory_embeddings"
        ).fetchall()
        scored = []
        for row in rows:
            cached = blob_to_embedding(row["embedding"])
            sim = cosine_similarity(query_embedding, cached)
            scored.append((row["memory_id"], sim))
        scored.sort(key=lambda x: -x[1])
        return scored[:limit]

    def _encode(self, text: str) -> list[float]:
        if self._model is None:
            self._load_model()
        return self._model.encode(text).tolist()

    def _load_model(self):
        """延迟加载 sentence-transformers 模型。"""
        from sentence_transformers import SentenceTransformer
        self._model = SentenceTransformer('BAAI/bge-small-zh-v1.5')
```

#### 3.3.3 RRF 融合排序

```python
def reciprocal_rank_fusion(
    ranked_lists: list[list[tuple[str, float]]],
    k: int = 60
) -> list[tuple[str, float]]:
    """
    Reciprocal Rank Fusion 融合多路排序结果。

    公式：RRF_score(d) = Σ 1 / (k + rank_i(d))
    其中 k=60 是平滑常数，rank 从 1 开始。
    """
    scores: dict[str, float] = {}
    for ranked_list in ranked_lists:
        for rank, (doc_id, _score) in enumerate(ranked_list, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    # 按 RRF 得分降序排列
    return sorted(scores.items(), key=lambda x: -x[1])
```

### 3.4 上下文三级压缩策略

三级压缩在每次 LLM 调用前检查，由 `Compressor` 类统一管理：

| 级别 | Token 阈值 | 策略 | 保留内容 |
|------|-----------|------|----------|
| **Level 1** | 8K token（~5600 字符） | 软限制 — 早期消息摘要化 | 当前轮完整 + 上一轮完整 + 摘要 |
| **Level 2** | 15K token（~10500 字符） | 硬限制 — 激进摘要 + 工具结果压缩 | 当前轮完整 + 上一轮摘要 + 工具结果首尾 |
| **Level 3** | 25K token（~17500 字符） | 紧急截断 — 仅保留当前轮 | 当前轮用户消息 + 最近 1 条工具结果 |

```python
class ContextCompressor:
    """三级上下文压缩器。"""

    LEVELS = [
        {"threshold": 8000, "strategy": "early_summary"},
        {"threshold": 15000, "strategy": "aggressive_summary"},
        {"threshold": 25000, "strategy": "emergency_truncate"},
    ]

    def compress(self, messages: list[dict], *, store, session_id: str) -> list[dict]:
        token_estimate = self._estimate_tokens(messages)
        level = self._determine_level(token_estimate)

        if level == 0:
            return messages  # 未达阈值，不压缩

        # 分离当前轮和历史消息
        current_turn = self._extract_current_turn(messages)
        history = messages[:len(messages) - len(current_turn)]

        if level >= 1:
            # 将早期消息压缩为摘要
            summary = self._summarize(history[:-len(current_turn)])
            self._save_summary(store, session_id, summary, level=level)

        if level >= 2:
            # 激进压缩工具调用结果
            current_turn = self._compress_tool_results(current_turn)

        if level >= 3:
            # 紧急截断：仅保留当前轮用户消息
            current_turn = self._emergency_truncate(current_turn)

        return self._rebuild_messages(summary, current_turn)

    def _estimate_tokens(self, messages: list[dict]) -> int:
        """粗略估算 token 数（中文约 1.5 字/token，英文约 4 字符/token）。"""
        total_chars = sum(len(str(m.get("content", ""))) for m in messages)
        return int(total_chars / 1.5)  # 保守估算

    def _determine_level(self, tokens: int) -> int:
        for i, level in enumerate(reversed(self.LEVELS)):
            if tokens > level["threshold"]:
                return len(self.LEVELS) - i
        return 0
```

**压缩产物存储**：压缩摘要由 `ContextBudgeter` 管理，存入会话状态（`run_runtime.context_summary`），与现有机制保持一致。`compressor.py` 仅提供压缩策略函数，不负责持久化。

#### 3.5.2 记忆强度模型

```python
def calculate_strength(memory: dict, now: float) -> float:
    """
    计算记忆强度。强度低于阈值的记忆将被归档。

    公式：strength = importance × 0.4 + frequency_factor × 0.3 + decay_factor × 0.3

    其中：
    - importance: 记忆创建时设定的重要度（0~1）
    - frequency_factor: 访问频率因子，基于 access_count 和创建时长
    - decay_factor: 时间衰减因子，基于半衰期模型
    """
    importance = memory.get("importance", 0.5)

    # 频率因子：归一化访问频率（对数缩放）
    age_days = max(1.0, (now - memory["created_at"]) / 86400)
    access_count = memory.get("access_count", 0)
    frequency_factor = min(1.0, math.log(1 + access_count) / math.log(1 + age_days * 0.5))

    # 衰减因子：指数衰减，半衰期随重要度变化
    last_used = memory.get("last_used_at") or memory["created_at"]
    idle_days = (now - last_used) / 86400
    half_life = 7 + importance * 53  # 7天（importance=0）~ 60天（importance=1）
    decay_factor = 0.5 ** (idle_days / half_life)

    return importance * 0.4 + frequency_factor * 0.3 + decay_factor * 0.3
```

**半衰期公式说明**：

| importance | 半衰期 | 含义 |
|-----------|--------|------|
| 0.0 | 7 天 | 低重要度记忆一周后衰减 50% |
| 0.3 | 22.9 天 | 中等偏低重要度记忆约三周后衰减 50% |
| 0.5 | 33.5 天 | 中等重要度记忆约一个月后衰减 50% |
| 0.8 | 49.4 天 | 高重要度记忆约七周后衰减 50% |
| 1.0 | 60 天 | 最高重要度记忆两个月后衰减 50% |

#### 3.5.3 定期维护任务

```python
class LifecycleManager:
    """记忆生命周期管理器。"""

    def run_maintenance(self, conn: sqlite3.Connection, *, run_id: str | None = None):
        """执行定期维护：归档、遗忘、验证。"""
        now = time.time()

        # 1. 归档低强度记忆（strength < 0.2 且 30 天未使用）
        archived = self._archive_weak_memories(conn, now, run_id=run_id)

        # 2. 物理删除过期遗忘记忆（forgotten 超过 30 天）
        deleted = self._purge_expired_forgotten(conn, now, run_id=run_id)

        # 3. 验证来源文件有效性
        invalidated = self._validate_sources(conn, run_id=run_id)

        # 4. 记录维护日志
        self._log_maintenance(conn, archived, deleted, invalidated, run_id)

        return {"archived": archived, "deleted": deleted, "invalidated": invalidated}

    def _archive_weak_memories(self, conn, now, *, run_id) -> int:
        thirty_days_ago = now - 30 * 86400
        rows = conn.execute("""
            SELECT id, importance, access_count, created_at, last_used_at
            FROM memories WHERE status = 'active'
        """).fetchall()
        to_archive = []
        for row in rows:
            strength = calculate_strength(dict(row), now)
            last_used = row["last_used_at"] or row["created_at"]
            if strength < 0.2 and last_used < thirty_days_ago:
                to_archive.append(row["id"])
        if to_archive:
            conn.executemany(
                "UPDATE memories SET status='archived', updated_at=? WHERE id=?",
                [(now, mid) for mid in to_archive]
            )
            conn.commit()
        return len(to_archive)

    def _purge_expired_forgotten(self, conn, now, *, run_id) -> int:
        thirty_days_ago = now - 30 * 86400
        cursor = conn.execute("""
            DELETE FROM memories WHERE status = 'forgotten' AND updated_at < ?
        """, (thirty_days_ago,))
        conn.commit()
        return cursor.rowcount
```

```python
def check_semantic_duplicate(conn: sqlite3.Connection, new_embedding: list[float],
                             threshold: float = 0.90) -> tuple[str, float] | None:
    """检查是否存在语义相似的记忆（余弦相似度 > threshold）。"""
    rows = conn.execute(
        "SELECT memory_id, embedding FROM memory_embeddings"
    ).fetchall()
    best_match = None
    best_sim = 0.0
    for row in rows:
        cached = blob_to_embedding(row["embedding"])
        sim = cosine_similarity(new_embedding, cached)
        if sim > best_sim:
            best_sim = sim
            best_match = row["memory_id"]
    if best_match and best_sim > threshold:
        return (best_match, best_sim)
    return None
```

#### 3.6.3 去重失败时合并策略

```python
def merge_memory_content(existing: dict, new_content: str, new_summary: str,
                         new_keywords: list[str]) -> dict:
    """
    将新信息合并到已有记忆中。

    合并规则：
    - summary: 如果新摘要包含旧摘要中没有的关键信息，追加
    - content: 追加新内容段落，去重已有段落
    - keywords: 取并集
    """
    merged = dict(existing)
    # 合并关键词（取并集）
    old_kw = set(json.loads(existing["keywords"]))
    merged_kw = sorted(old_kw | set(new_keywords))
    merged["keywords"] = json.dumps(merged_kw, ensure_ascii=False)
    # 追加新内容（如果不同）
    if new_content.strip() not in existing["content"]:
        merged["content"] = existing["content"].rstrip() + "\n\n" + new_content.strip()
    # 更新摘要（如果新摘要更丰富）
    if len(new_summary) > len(existing["summary"]):
        merged["summary"] = new_summary
    return merged
```

### 3.7 智能 Prompt 注入

替换 `context_budgeter.py` 中现有的粗放注入逻辑，改为按综合得分选择记忆：

```python
class MemoryInjector:
    """智能记忆注入器。"""

    TOKEN_BUDGET = 2000        # 记忆注入 token 上限
    TYPE_PRIORITIES = {         # 类型优先级权重
        "gotcha": 1.0,
        "convention": 0.9,
        "architecture": 0.85,
        "dependency": 0.8,
        "command": 0.7,
        "project": 0.7,
        "decision": 0.6,
        "issue": 0.6,
        "character": 0.5,
        "world_setting": 0.5,
        "plot_thread": 0.5,
        "style_rule": 0.5,
    }

    def select_memories(self, conn, query: str, *, limit: int = 10) -> list[dict]:
        """
        按综合得分选择要注入的记忆。

        综合得分 = retrieval_score × 0.5
                 + importance × 0.2
                 + recency × 0.15
                 + type_priority × 0.15
        """
        # 获取检索结果（FTS5 或混合检索）
        candidates = self._retrieve(conn, query, limit=limit * 3)
        now = time.time()
        scored = []
        for mem in candidates:
            retrieval_score = mem.get("score", 0.0)
            importance = mem.get("importance", 0.5)
            # 新鲜度：最近 7 天 = 1.0，30 天 = 0.5，90 天 = 0.1
            age_days = (now - mem["updated_at"]) / 86400
            recency = max(0.0, 1.0 - age_days / 90)
            type_priority = self.TYPE_PRIORITIES.get(mem["type"], 0.5)

            total = (retrieval_score * 0.5
                     + importance * 0.2
                     + recency * 0.15
                     + type_priority * 0.15)
            scored.append((total, mem))

        scored.sort(key=lambda x: -x[0])

        # 在 token 预算内选择
        selected = []
        tokens_used = 0
        for score, mem in scored:
            mem_tokens = self._estimate_tokens(mem)
            if tokens_used + mem_tokens > self.TOKEN_BUDGET:
                break
            selected.append(mem)
            tokens_used += mem_tokens

        return selected

    def format_injection(self, memories: list[dict]) -> str:
        """格式化记忆注入文本。"""
        if not memories:
            return ""
        lines = ["## 项目记忆（按相关度排序）"]
        for mem in memories:
            lines.append(f"- **[{mem['type']}]** {mem['title']}: {mem['summary']}")
        return "\n".join(lines)
```

### 4.2 确定性破坏点

以下两处是重构后**必然失败**的点，必须在 P1 阶段同步修复：

**破坏点 1：`cli.py` 第 401 行 — 内部属性直接访问**

- 现状：`manager.data['changes'][-20:]` 直接访问 MemoryManager 的内部 `data` 字典
- 问题：重构后 `data` 属性不存在（改为 SQLite 连接），会抛 `AttributeError`
- 修复：在 MemoryManager 上新增 `recent_changes(limit=20)` 公共方法，修改 cli.py 调用新方法

**破坏点 2：`test_upgrade_p2_p6.py` 第 100 行 — 存储格式断言**

- 现状：断言 `memory.index_path.suffix == ".json"` 和 `(memory.root / entry["content_path"]).suffix == ".md"`
- 问题：重构后存储格式变为 SQLite，不再有 `.json` 索引和 `.md` 正文文件
- 修复：将格式特定断言替换为行为断言（检查 `read()` 返回正确 content，而非检查文件后缀）

### 4.3 FTS5 中文分词问题

实测发现 SQLite FTS5 的 `unicode61` tokenizer 对中文按**单字分词**：

- "项目架构" → "项" "目" "架" "构"
- 搜索"项目"会匹配所有包含"项"或"目"的条目，召回率过高、精度不足

缓解措施（按优先级）：

1. 对中文查询使用双引号强制短语匹配（`"项目"` → 精确匹配"项目"二字相邻）
2. 利用 BM25 权重（title 10x, keywords 5x）让精确匹配排在前面
3. 如精度仍不够，引入 `jieba` 分词作为可选依赖
4. P10 的 Embedding 语义检索可根本性解决此问题

### 4.4 Top 5 工程风险

**风险 1：JSON → SQLite 迁移数据丢失**

- 概率：中（30%）| 影响：极高
- 缓解：迁移前完整备份；迁移后逐条校验条目数+关键字段；旧文件保留不删除；增加迁移后自动化验证测试；**迁移失败时自动回滚到 JSON 模式**

**风险 2：`manager.data` 内部属性直接访问导致运行时错误**

- 概率：极高（100%）| 影响：高
- 缓解：新增 `recent_changes(limit)` 公共方法替代；修改 cli.py 第 401 行；全局搜索 `manager.data` 确保无其他直接访问

**风险 3：上下文压缩摘要质量不足**

- 概率：中（40%）| 影响：中
- 缓解：优先采用规则提取（与现有 `compact()` 策略一致）；仅在 Level 3 紧急截断时考虑 LLM 摘要；保留现有 `user_goals` + `assistant_results` + `changes` + `source_refs` 结构化提取逻辑

**风险 4：现有测试断言存储格式导致 CI 失败**

### P3: 记忆生命周期管理

**具体任务**：

1. **创建 `lifecycle.py`**
   - 实现 `LifecycleManager` 类
   - 实现 `calculate_strength(memory, now)` 函数：
     - `strength = importance × 0.4 + frequency_factor × 0.3 + decay_factor × 0.3`

## 9. 风险与应对

### 9.1 迁移数据丢失风险

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|----------|
| JSON→SQLite 迁移过程中数据丢失 | 用户记忆永久丢失 | 低 | **保留旧文件备份**：迁移前将 `index.json` 重命名为 `index.json.migrated`，`entries/` 目录保留不删除。迁移完成后校验条目数一致，不一致则回滚。 |
| 迁移脚本 bug 导致字段映射错误 | 部分字段数据错误 | 中 | **逐字段验证**：迁移后对每条记忆逐字段比对，确保 title/summary/content/keywords 等关键字段一致。编写专门的 `test_migration.py` 覆盖。 |

### 9.2 SQLite 并发冲突

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|----------|
| 多进程同时写入导致 SQLITE_BUSY | 写入失败 | 低 | **启用 WAL 模式**：`PRAGMA journal_mode=WAL` 允许读写并发。设置 `timeout=10.0` 秒等待锁释放。写入失败时重试 3 次。 |
| WAL 文件无限增长 | 磁盘空间占用 | 低 | 定期执行 `PRAGMA wal_checkpoint(TRUNCATE)` 清理 WAL 文件。 |

### 9.3 Embedding 模型体积大

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|----------|
| `sentence-transformers` + `bge-small-zh-v1.5` 约 400MB | 安装体积增大 | 高 | **可选安装**：作为 extra 依赖，`pip install genesisai[embedding]`。未安装时优雅降级为纯 BM25 检索。延迟加载模型，首次检索时才加载。 |
| 模型加载耗时 2~5 秒 | 首次检索延迟 | 高 | **延迟加载**：模型在首次检索请求时才加载到内存，不影响 CLI 启动速度。后续请求复用已加载的模型实例。 |

### 9.4 压缩丢失关键信息

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|----------|
| Level 2/3 压缩丢失工具调用结果 | Agent 无法引用之前的工具输出 | 中 | **工具结果单独提取**：压缩时将工具调用结果（文件变更、测试结果、错误信息）单独提取保留，不与普通消息一起摘要化。 |
| 压缩摘要质量差 | LLM 无法理解早期上下文 | 中 | **结构化摘要**：摘要采用 JSON 格式，包含 user_goals、assistant_results、changes、source_refs 等字段，确保关键信息不丢失。 |

### 9.5 API 兼容性

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|----------|
| 重构后 MemoryManager API 行为变化 | 下游工具报错 | 中 | **保持签名不变**：构造函数、add()、search()、read()、forget() 等方法签名和返回值结构完全不变。通过回归测试验证。 |
| dict 字段名变化 | 下游解析失败 | 低 | **字段名保持一致**：返回值 dict 的 key 与旧版完全一致。新增字段（如 strength）仅在新模块中使用。 |

### 9.6 性能回退

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|----------|
| SQLite 查询比 JSON 内存遍历慢 | 检索延迟增加 | 极低 | **索引优化**：为高频查询路径建立索引。SQLite 内存查询在数据量 < 10000 时通常快于 JSON 全量加载。通过性能测试持续监控。 |
