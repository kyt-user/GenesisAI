# 交互运行与队列审计（2026-11-04）

范围覆盖交互 CLI 的提交、取消、恢复、子进程生命周期、流式终端和运行日志。检查对象为当日 Windows 工作树。复跑交互队列、终端输入、流式输出和 CLI 界面四组测试，48 项通过。下文记录修复前的复现现象与当时的代码位置。勾选项表示修复已通过对应验收。本次使用临时会话、模拟模型和短时本机子进程。

### P1 · 已启动的命令在取消后被记录为未执行

- [x] 让一次取消即可终止运行并暂停队列，在工具账本和交付给模型的消息中保留“已启动，可能产生部分副作用”。继续禁止重放结果不确定的调用。
- 复现中命令先写入标记文件，再输出一行并等待。此时发出与 `/cancel` 相同的信号，文件存在，子进程退出，但运行落为 `interrupted`，工具账本落为 `unknown`。`/queue resume` 的前置检查拒绝继续。再次取消后，工具消息写为“工具未执行”。
- 受控命令把工作目录用作预览目标。异常分支以目标存在判断执行结果不确定，Runner 在检查取消之前就返回中断。二次取消时又对所有待处理调用使用同一条未执行文案。定位见 `core/tools/executor.py:89–103`、`agent/loop.py:265–268, 506–509`（源码路径均相对 `src/genesisai/`）。

### P1 · 排队消息在新一轮成功登记前出队

- [x] 区分工作线程接单和新一轮完成登记。登记前失败应暂停并保留队首，已登记且可能产生副作用的任务禁止自动重放。
- A 运行时排入 B、C，在 B 的启动前校验中注入缺失的历史网页快照，由真实的 `Store.verify_sources()` 报错。此时 `/queue` 只剩 C，恢复后会话用户消息为 A、C。B 仍可在输入日志中查到。
- `start_next()` 在线程池接受任务后立即移除队首。历史来源校验、生成新 run ID 和持久化用户消息都发生在工作线程内。定位见 `app/cli.py:429–438`、`agent/loop.py:129–136, 198–215`。

### P1 · Windows 宿主异常退出后，受控命令可以继续写文件

- [x] 在子进程启动前设置 Windows Job 的 `KILL_ON_JOB_CLOSE` 限制，并添加宿主异常终止的进程树验收。
- 隔离宿主通过生产 `owned_process()` 启动一个短时子进程，随后调用 `os._exit(0)`。子进程在宿主退出后仍成功写入标记文件。现有回归覆盖正常取消，以及命令启动器先退出的情况。
- Job 未启用关闭最后一个句柄时终止成员的限制，进程树回收依赖 Python 执行 `finally`。定位见 `core/extensions/tools/shell/process_tree.py:26–44`。

### P2 · 工具的输出可以改变终端画面

- [x] 在输出到终端的边界把不受信任的控制序列转为可见文本或移除，同时保留正常换行。测试覆盖 CSI 清屏、移动光标和 OSC 序列。
- 把含 `ESC[2J` 的一行命令输出送入真实 `CliView.render_progress()`，捕获到的 Rich 输出保留了完整控制序列。支持 VT 的终端可以执行其中的清屏指令，影响用户对运行过程的观察。该复现捕获输出字节，未对用户的终端发送清屏指令。定位见 `app/terminal_view.py:332–335`。

### P2 · 大量短行输出会积压在终端事件队列

- [x] 批量传递实时输出，为界面缓冲设置上限。完整输出可落盘，耗时的终端回放不应阻塞接收控制命令。
- 受控命令打印 20,000 行，共 40,000 字符。按界面的每批 128 条、间隔 50 ms 消费，使用空渲染函数，在本次采样中命令完成时仍有 19,872 条事件待处理。CLI 在接收下一次输入前同步清空余量。输出量更大时，内存和回放时间都随之增长。
- 定位见 `core/extensions/tools/shell/process.py:52–53, 84–86`、`app/run_queue.py:20`、`app/command_input.py:145–154`、`app/cli.py:444–447`。

### P2 · 队列启动日志归到了上一轮

- [x] 使用稳定的队列项 ID 关联入队、调度和运行事件。在新一轮身份确定后记录绑定，区分已调度和已开始。
- 在本轮回归生成的 JSONL 中，B 的 `queue_start` 带 A 的 run ID，C 的带 B 的 run ID。UI 写日志时从共享会话读取当前 run ID，与后台分配新 ID 的顺序没有保证，按 run ID 查日志会归错轮次。定位见 `app/cli.py:435–438`、`core/state/io_journal.py` 的 `write()` 和 `agent/loop.py:198`。

## 修复验收

- 运行取消覆盖直接执行和批准后执行两种路径。命令先写文件再取消，账本和工具消息均保留已启动及可能留下修改的信息。恢复时取消结果不确定的历史调用，保留原始调用结果。
- 对队首的首次会话保存和登记后的保存分别注入失败。前者恢复后仍执行原队首，后者继续下一项。按 queue_id 检查入队、调度、启动与最终 run_id 的关联。
- Windows 验收从外部强制终止测试宿主，持有子进程和孙进程的句柄并验证两者退出。
- CSI、OSC 和 C1 控制字符通过真实 Rich 输出边界检验，实时输出及详情中都没有可执行的原始序列。
- 在终端尚未消费事件时运行 20,000 行标准输出和一行标准错误。待显示的命令输出合并为一个有界事件，日志分流拼接后与原文一致。
