# 下一阶段主要目标

日期：2026-11-09。状态：方向已确认，具体实施待启动。

本阶段承接[当前阶段收尾声明](2026-11-09-stage-closeout.md)。后续修改集中于 BUG 修复、能力扩展、长任务支持和 UI 能力增强。本文是后续工作的主入口；下列未勾选项是待实施目标，不代表当前已支持。

## 优先级与实施原则

1. 影响使用的 BUG 优先修复，保留复现条件、原因、修复及回归证据。
2. 长任务支持作为核心建设，把详细需求落实为可执行、可追踪、可验收的任务清单。
3. UI 能力逐步补齐前端制作、观察、操作和验证流程。
4. 能力扩展优先增强围绕任务自主发现、选择和调用能力，以及发现缺口后衔接接入或构建的流程；其他扩展按实际收益安排，不以工具数量作为完成标准。

保持单 Agent 主会话定位。多 Agent、常驻调度服务和更多产品入口不作为本阶段的默认交付目标；如后续需要，另行明确范围。ENV 优先、终端密钥回退、会话恢复、错误处理和现有授权规则继续作为正式功能维护。遵循 [AGENTS.md](../AGENTS.md)，不覆盖未提交改动，不擅自删除用户数据，不为旧接口新增兼容层。

## A. BUG 修复

- [ ] **BUG-01：形成可追踪的问题清单。** 根据真实使用和回归结果记录问题；每项包含复现步骤、环境、影响、优先级和证据。优先处理错误退出、卡住、任务状态不一致、恢复失败和错误宣称完成。
- [ ] **BUG-02：逐项修复并验证。** 修复原因而非仅隐藏现象；同步更新受影响的调用方、测试和文档，对失败场景及相关正常路径做针对性回归。

验收标准：每个关闭的问题都有可复现的原始失败及修复后证据；未复现、未验证、环境受限与已修复明确区分，不把历史审计中的所有旧条目直接视作当前未解决问题。

## B. 能力扩展

本主线的优先关注点是 **任务驱动的能力自主发现、选择与调用**，包括使用已有 Tool、Skill、MCP，以及发现能力缺口后提出接入或构建方案。

当前已有机制：Agent 可调用 `discover_tools` 查找并加载可用工具；`/create_tool`、`/create_skill`、`/create_mcp` 是构建任务的快捷入口，对应底层工具也可由模型调用，自然语言构建需求可以进入相同流程。当前协议规定普通任务不自动创建永久能力，用户明确要求可复用能力或进入创造模式后才构建；正式注册仍需当前版本测试通过和用户明确验收。下一阶段不能把这些已有机制误写成完全缺失，也不能把“接口可调用”直接视为自主决策已可靠。

- [ ] **CAP-01：验证并增强自主选择与调用。** 用户只描述任务目标时，Agent 能检查已有能力、按需发现并选用合适的 Tool／Skill／MCP，在授权范围内执行并继续原任务；不要求用户记住工具名或逐步输入斜杠命令。明确“有可用能力但没发现/没调用”和“确实缺少能力”的区别。
- [ ] **CAP-02：识别缺口并衔接构建。** 确认已有能力无法满足需求后，说明缺口及可行替代路径，提出接入或构建方案；在用户明确授权构建后完成实现、测试和验收，并将可用结果衔接回原任务。模型适配、语言服务或其他集成也须列明场景、依赖和预期结果后再安排实施。普通任务自动创建永久能力的策略如需改变，另行明确产品决定，不在本目标中默认放开。
- [ ] **CAP-03：打通发现、调用与验证。** 新能力接入现有工具发现、权限、结果与错误处理流程；需要时复用能力构建、测试、试用和注册机制。
- [ ] **CAP-04：完成真实任务验收。** 至少覆盖“已有能力可用”“能力存在但尚未加载”“确实缺失并经授权构建”三类场景；每项扩展覆盖实际使用及相关失败路径，说明依赖缺失、授权不足或模型能力不匹配时的行为，并同步使用文档。

验收标准：从自然语言任务出发，Agent 能找到并正确调用所需能力，缺口处理有明确下一步，能力可用后能够继续原任务，产物和执行结果可以核对。正式注册继续要求用户验收；工具注册成功、配置存在、脚本模型预设了工具调用或提示词描述不能单独作为自主选择能力的交付证据。

## C. 长任务支持

目标流程：**理解需求 → 制定计划与任务清单 → 实施 → 分项验收 → 整体验收 → 交付。**

- [ ] **LONG-01：从详细需求生成任务清单。** 提取目标、约束、交付物和验收条件；缺少关键条件时澄清，将复杂任务拆成可独立推进和验证的步骤。
- [ ] **LONG-02：明确任务依赖与状态。** 每项至少记录任务编号、内容、依赖、状态、完成条件、验证方式和结果证据；能区分待执行、执行中、受阻、待验收与已验收。
- [ ] **LONG-03：提供显式 `/plan` 入口。** 支持进入调查与讨论阶段、查看和调整计划、明确转入实施；规划阶段的修改限制由执行层落实，不能只依赖提示词。先界定可用工具及命令范围，再实现模式切换。
- [ ] **LONG-04：按计划执行并更新进度。** 根据依赖选择下一项，记录实际修改、执行结果和阻塞原因；用户补充或修改需求时更新计划及受影响任务，避免仍按旧清单推进。
- [ ] **LONG-05：分项验收与整体验收。** 每项完成后执行对应检查；最后核对全部需求及跨任务集成结果。验证失败或证据缺失时回到修复/待验收状态；源码或需求变化后重新判断原验收是否仍有效。
- [ ] **LONG-06：中断恢复与计划调整。** 恢复时还原清单、进度、证据和待处理作业，核对工作区变化；不重复执行结果未知且可能有副作用的操作。计划调整保留原因和受影响范围。
- [ ] **LONG-07：用跨阶段真实任务评估。** 覆盖多文件功能开发、跨模块重构、执行中需求变化、失败修复和中断恢复，记录实际完成情况、人工介入、耗时及可获取的模型用量。

验收标准：用户能够查看要做什么、做到哪一步、为何受阻及凭什么判定完成。至少完成一条包含多项依赖、失败修复、中断恢复和整体验收的真实任务链；任务清单不能仅作为展示文本，状态必须与执行和验收事实关联。

已有任务账本、版本化验收与会话恢复是实施基础，应先核对并复用当前设计。这里要求增强其长任务使用效果，不另建一套互不关联的状态系统。

## D. UI 能力增强

这里的 UI 指 **Genesis 开发和调试前端页面的能力**，包括布局、样式、响应式及交互效果；终端界面或桌宠外观不替代这条主线的交付。

- [ ] **UI-01：增强页面实现与修改。** 能根据需求和可用参考实现或调整页面结构、视觉层次、布局、样式及不同视口下的表现，并保持项目已有设计约定。
- [ ] **UI-02：接入交互式浏览器验证。** 在现有授权规则下访问开发页面，支持必要的导航、点击、输入和滚动，检查交互后的实际状态。现有 GET 页面读取器不直接视为已具备这些能力。
- [ ] **UI-03：建立观察与反馈渠道。** 获取页面截图、相关控制台错误和运行结果；视觉判断依赖支持图片输入的模型，明确所需模型、浏览器和其他环境条件。
- [ ] **UI-04：完成修改后的再次验证。** 将页面操作与观察结果用于修复，再重新执行对应操作和截图检查，保留能说明效果的前后证据。
- [ ] **UI-05：覆盖代表性前端任务。** 至少覆盖页面从零构建、已有页面样式调整、响应式问题修复及表单/导航交互；分别检查视觉效果、交互行为和构建结果。

验收标准：在真实运行的前端项目中完成“实现 → 打开页面 → 操作与观察 → 修正 → 再次验证”，交付可核对的截图及交互结果。构建通过、静态 HTML 检查或读取到 DOM 不能单独证明视觉和交互验收通过。

- 实施后补充提交、测试或人工验收证据，再更新清单状态。普通文档修改按内容、链接和差异核对，代码修改按影响选择测试。
- 建立固定的代表性开发任务集，区分受控仿真和真实模型结果；如与原版 Cline 比较，固定模型、任务、预算和环境，并记录差异。
- 本阶段结束时逐项说明已完成、受阻或延期的目标及原因，形成新的阶段收尾记录；不以工具数量、单元测试数量或计划勾选数代替实际任务完成能力。
